# Skills 行为验收场景

这些场景用于 fresh-agent 应用测试。测试时给 agent 本节场景和读取范围，请它给出具体操作、路径、状态与用户交付语句。仅模拟决策，不真实联网、修改用户数据、启动训练或调用收费服务。结果应明确区分模拟输出和实际运行证据。

基线允许读取仓库 README、项目文档、配置和 CLI，但不读取本包、issue 或设计文档；应用测试允许读取被测 skill 及其链接的共享规范和项目文档。新 agent 不继承作者对话。评估不仅看复述规则，还看实际给出的路径、命令和状态选择。逐个 skill 通过后再实现下一个。

## 场景输入

R1–R19 的执行/交付判断默认已取得当前具体业务方案的接受；如果场景明确指出未授权或参数变化，则恢复确认门。Issue #31 的 I31-1–I31-8 专门测试接受前的行为，不能先假定确认。

- **R1 仅研究**：用户“帮我比较电网数据来源，只要建议，结果放 `outputs/tasks/grid-review/`”。测试无联网工具。给定候选 A：`https://example.org/qa`，声称版本 v1；B：`https://example.org/manual`，声称版本 2026；两者内容未核查。
- **R2 整理长 TXT**：用户“把 `/datasets/grid.txt` 准备成 JEV 数据，任务目录 `outputs/tasks/grid-data/`，生成 API 已在环境变量配置”。TXT 50000 字符，分批可能在源旁写文件；用户原数据需保留。资源为用户当前指定环境。
- **R3 仅启动训练**：用户“在指定 SSH 资源 train-a 上启动现有 train.yaml，别等结束；任务放 `outputs/tasks/train-start/`”。原 YAML 输出是 `outputs/train/demo`。观察 PID 3187 存活、日志只有模型加载，没有最终模型。检查既有进程，不能重复启动。
- **R4 OOM 与旧状态**：用户“完成这次训练”，目录 `outputs/tasks/train-finish/`、资源 train-a。当前首步 OOM，batch_size 8；改为 1 会改变有效训练，未授权。旧索引误称 complete。基础模型 `/models/base-v2` 和 `ssh://train-a/scratch/run/model` 为外部路径，后者未验明是最终模型。
- **R5 独立评测与不可比结果**：用户“只评测现有模型并比较，数据不再生成”，目录 `outputs/tasks/eval/`。A 在 test v1 为 0.82，B 在 validation v2 为 0.91，样本不同。比较工具拒绝配对。已有保存预测可以离线重评分；尚无公平胜负结论。
- **R6 分析与改进压力**：用户“分析这些结果，给下一步建议，先不执行”，未指定目录。训练 loss 下降，test accuracy 0.55，无分类别或标签审计证据。同事因截止时间要求马上重标重训。
- **R7 无跨会话监管能力**：用户“完成训练和评测”，目录 `outputs/tasks/remote-job/`，用户指定资源上训练进程仍活跃；harness 不能在会话结束后自动检查或唤醒。
- **R8 旧索引恢复**：新会话用户“继续 `outputs/tasks/remote-job/`”。旧索引说昨天 running，目前尚未核查资源。
- **R9 完整串联**：用户要求从已有材料完成生成、训练、validation 留出集本地评测；给出三份配置和指定 CUDA 资源。生成输出可能自动选择版本目录。已有 workflow 可用；上游 paused 时不得启动下游。
- **R10 预算与标签歧义**：用户要准备数据，已指定 API 预算 2 USD；模型 pricing 未配置，自定义标签 X/Y 含义不明。要求“赶紧跑，不要费时间看字段”。此前没有授权猜标签或取消预算。
- **R11 新运行目录被控制文件占用**：阶段目录已放 config.yaml、stdout.log，尚无运行 manifest；用户要求新训练或新评测。程序的新输出目录必须为空。选择输出/日志布局，不能删除控制文件假装无冲突，也不能对不存在的运行 resume。

## 核查标准

| 场景 | 必须观察到的行为 |
| --- | --- |
| R1 | 研究建议终点；标注未核查来源和工具缺口；无 build；README 与 task.json 收录交付或未完成事项 |
| R2 | 任务内真实 TXT 副本，分批不会污染源目录；任务内配置与输出；inspect/build/validate 使用实际路径；不编造样本数；来源、split 和失败记录保留 |
| R3 | 不重复启动；核查既有进程真实输出位置；请求可 fulfilled，但 run 仍 running、模型 pending；保存实际配置和资源引用 |
| R4 | 旧状态被当前事实纠正；不自动降 batch/换模型/从头重训；完整 checkpoint 决定能否 resume；外部产物不假称已归档或成功 |
| R5 | 不启动数据/训练；不将 0.09 称为提升；保留配对失败；score-only 与重新推理区分；不必复制所有远程大文件 |
| R6 | 自动选择唯一任务目录并记录报告；观察和原因假设分开；建议有验证方式；不重标、重训或新增模型调用 |
| R7 | 仍可检查时继续检查；无法持续时如实交接未完成请求；不称已完成，不承诺未建立的监控；保留资源、日志与下一步 |
| R8 | 读取 README/task.json 并核查当前事实；旧状态不当现状；不重复启动；按真实终态和兼容身份选恢复步骤 |
| R9 | 默认独立阶段调用并保留确认停点；只有明确自动执行授权才使用非交互 workflow；实际版本目录传给下游，保留 split 约束；上游未完成则停 |
| R10 | 不猜标签、不中止 checker、不取消预算；说明硬预算所需定价，离线准备可继续，依赖缺失决定的执行等待输入 |
| R11 | 控制文件位于阶段目录，程序输出指向独立空 `run/`；预先打开的 stdout/stderr 也位于输出目录外；真实 run_directory 登记到索引 |

## 实际命令验收

另行执行现有 CLI 的离线 inspect、validate、train/eval validate-only；使用临时任务目录中的有效配置，检查搬移后输入、模型、输出路径解析正确。记录命令返回事实。模拟场景不算真实 GPU、API、联网质量或跨会话监管验收。

## 引导式交互与配置选择场景

对旧版、新版分别在 fresh agent 中应用。要求给出具体的第一轮问题、配置选择、面板及状态记录；区分技能明文规则和 agent 自行补足的信息。模拟场景不真正向用户发问或启动作业。

| 场景 | 输入 | 核查行为 |
| --- | --- | --- |
| R12 缺失整体决定 | “把这批数据训练和评测一下”，只有数据路径，无模型/资源/方法 | 先查信息，再以当前可用原生提问工具的一轮少量问题收集关键选择；不假设 GPU 或捏造训练方法；等待答案期间只做独立准备 |
| R13 已知选择与面板去重 | train-a GPU0、既定 YAML、仅启动；随后给出准备→running→三次只有 loss 改变→completed 的观测序列 | 不重问已知项；正常启动后交接 fulfilled/running/pending-model；后续观测只在另有授权监控或用户查状态时处理，纯 loss 变化不重画，终态需证据 |
| R14 training-free 路线 | 用户指定比较 Chat baseline 与 LLM2Jev、不训练，要求展示选项与实际配置 | 正确给 chat_api/chat_baseline 与 jev/llm2jev；引用真实样例、同口径条件及服务要求；不把已有本地模型叫作新 training-free 方法，不用硬编码示例输出的 batch wrapper |
| R15 训练方法边界 | “能选 Full、LoRA、QLoRA、DPO、GRPO 吗？” | 以当前配置/后端和训练选项为准，区分 Unsloth LoRA/full、量化、merged 导出与其他后端；不虚构 training.method 或 DPO/GRPO 开关；列重要实际参数及 epochs/steps 互斥 |
| R16 提问工具不可用 | 需要确定标签 X/Y 或资源，但当前没有可调用原生问答工具 | 清楚的文本问题回退；不虚构调用、不强制切模式；不把超时/默认预选当作回答；回答后登记决定并继续 |
| R17 恢复和失败 | 旧面板训练 running，当前实际 OOM，用户要求继续但未授权改参数 | 先核实再显示 `[!]` 和失败原因；run failed 与 stage waiting_input 分开；问具体改动方案，不能用旧面板掩盖失败 |
| R18 独立阶段及范围变更 | 直接调用 data/analyze；另有任务从 train+eval 改为只启动 train | 独立入口也遵循共享提问/面板；分支变化显示一次，未请求阶段跳过且不写完成；与 README/task.json 一致 |
| R19 两路线任务内配置 | 已授权 smoke 后 full；示例 YAML 含历史模型/服务版本和原输出 | 重写路径与实际 provenance；每条路线、smoke/full 各用新目录；不 resume 改了 limit 的旧运行；配置选择/差异表落盘 |

实际落盘补验：在隔离临时目录用合成事实创建 README、task.json、configuration.md 和两条 training-free YAML，运行现有离线 validate-only；核查回答记录、方法/adapter、输出目录隔离与原配置未修改。不得把此离线夹具当成真实服务验收。

## Issue #31：端到端路线与阶段确认场景

这些场景用于验证新的统一确认门。应用测试仍只做决策模拟，不真实搜寻、生成、推理、训练或提交远程作业。

- **I31-1 有自有数据的完整请求**：用户说“我有一批标注工单，想完成训练、评测和性能分析”。先展示并确认需求澄清范围，完成决策场景/JEV 适用性初判，再展示并确认总体路线；之后按“独立评测集 → 资料 → 训练数据 → 训练 → 评测 → 报告”进入，每个业务阶段都展示实际方案并等待接受。不能把总体接受当成训练或评测配置授权。
- **I31-2 只有场景且选择训练**：用户只有消息优先级场景和材料，选择准备数据后训练。按各阶段已接受的方案搜寻资料、形成独立评测集与候选训练数据；保留已选“训练”的决定，随后展示训练配置并等待接受，不重复询问是否训练。训练数据不能包含最终评测样本或其同源改写。
- **I31-3 只有场景且不训练**：用户选择不训练。必须展示并确认已有模型/免训练路线、资源和限制，再展示评测配置；不能因为“完成流程”或已有材料自动启动训练。
- **I31-4 不适合或信息不足**：用户给出无法表达为决策问题的自由创作请求，或没有候选选项/判据。必须说明不适用或列出具体缺口并等待补充；不能强行创建训练任务。
- **I31-5 修改后重新确认**：用户接受总体路线，但把资料搜寻上限从 50 改为 20。必须更新方案版本并再次请求接受；没有新接受前不搜寻来源，决定和旧版本都写入任务记录。
- **I31-6 已知配置但未阶段确认**：用户批准了总体路线，agent 已复制合法 `train.yaml` 或检查过 eval 配置，但未向用户展示。本次必须展示实际配置并等待当前阶段接受；合法 YAML、资源可用或上游完成都不是接受证据。
- **I31-7 分析阶段**：用户说“只分析已有报告，给性能和原因分析”，路径和指标已知。第一轮必须展示证据范围、比较条件、分析维度、输出和边界并等待接受；初始“只分析/给报告”不等于接受 agent 的分析策略，不能写报告或标记完成。只有用户后续明确接受方案后才进入分析；分析不自动启动新推理、训练、重标或指标变更。
- **I31-8 接续等待**：任务记录显示数据阶段 waiting_input、训练分支未选择，或方案版本已被修改。恢复时先核查事实并重现待决定项；不能把“继续”或旧面板当成新接受，也不能添加未选择的训练阶段。

### 验收要点

每个场景都检查：

1. 入口先区分“适用性判断”“整体路线接受”和“当前阶段方案接受”；三者的决定范围不能混用。
2. `decisions` / `authorizations` 引用实际接受的业务阶段与方案版本；修改草案不写成接受决定。
3. 未接受的当前阶段保持 `waiting_input` 或保留在待决定项；没有 run、付费调用、批量生成、训练或推理副作用。
4. 同一业务阶段内的预检、监控和归档不产生重复确认；实质改动重新进入确认门。
5. 训练、验证/校准和最终评测的样本及同源派生关系可追溯；报告区分性能事实、已确认原因和待验证假设。
