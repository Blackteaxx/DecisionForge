# 提问、配置选择与进度面板

所有入口共用本规范，包括直接调用某个阶段 skill。它约定 agent 与用户如何协作；运行事实和持久状态仍按 [任务记录](task-record.md) 与 [执行规则](execution.md) 保存。

## 业务阶段与内部步骤

默认每个业务阶段都先展示具体方案，再由用户接受或修改后执行；总体路线确认不代替本阶段参数确认。这个默认交互约定适用于五个入口及直接调用单阶段的请求。用户明确指定的交互方式和既有具体授权优先，不能把泛泛的“完成训练评测”解释为已确认所有后续配置。

业务阶段包括需求澄清、整体路线确认、整理评测集、搜寻资料、整理训练/场景数据、训练、选择已有模型或免训练方案、评测、报告分析。一个 skill 可以覆盖多个业务阶段，例如 `decisionforge` 的评测集整理、资料搜寻和训练数据整理需分别确认。文件里的 Stage 0–5、写 YAML、离线预检、监控、同一报告的统计与撰写是内部步骤，不逐命令增加确认门。

## 每阶段确认流程

1. **检查事实，形成方案。** 读取请求、已有配置、README/task.json 和必要的输入样本；整理已确定条件与缺口。允许做形成方案所需的只读检查、任务记录、配置草拟和不调用模型的离线预检。不得把资料搜寻、批量整理、生成、训练、推理或完整分析伪装成“准备”提前完成。
2. **展示当前阶段。** 展示目标、输入及版本、策略与关键参数、资源/预算及已知成本、预期产物与交付终点。未知值写明；推荐值标为建议。需求澄清先展示分析范围、判据和待澄清问题；整体流程阶段展示数据路径、训练选择、资源约束和本次终点。
3. **实际等待决定。** 即使没有缺失字段，也应明确提供“接受本方案／修改／暂停”的选择，等待用户对本阶段方案的决定。用户修改时更新方案并再次确认；不得收到修改意见后直接执行新方案。未回复、超时、默认预选、配置合法或“上一步已完成”都不是接受。
4. **记录后执行。** 将用户回答、业务阶段、方案版本/配置入口和授权范围写入 [任务记录](task-record.md)。没有接受时将当前阶段/请求标为 `waiting_input`，保留 `pending_decisions`；不得创建实际运行、发起付费调用或推进依赖它的下游。用户暂停时保存当前状态和继续方式，不轮询催促。
5. **核查并交接。** 按阶段终点核查产物，展示结果及证据，再进入下一业务阶段的方案展示与确认。失败或产物不可用时保留运行事实与证据，说明问题并提出具体调整方案，等待决定；不能让下游消费假定成功的产物。

### 已有确认、调整与接续

同一业务阶段、同一具体方案已被用户接受时，可展示沿用的配置和决定引用后继续，不重复确认每条命令、每次 loss 更新或重写同一份 YAML。用户主动提供明确、完整的当前阶段配置并明确要求执行，也可作为该具体方案的授权；只有文件路径、已知资源、总体路线、阶段名称/终点或“按默认值跑”但未确定实际适用配置时，不能据此跳过方案展示与确认。特别是“只分析”“给报告”“完成评测”这类初始范围请求，不等于接受 agent 后续拟定的分析/评测策略；请求指定的 endpoint 仍要经过当前方案门。

方法、数据含义/划分、关键参数、评测口径、资源/预算或交付终点发生实质变化时，展示差异及影响，重新等待确认；纯路径定位、既定依赖或连接故障可在原方案授权内修复并记录。已明确授权的有限恢复策略可沿用，不能扩张为任意改参。

跨会话先核查实际作业、产物和配置是否仍匹配，再展示恢复后的进展、当前方案及决定引用。原确认仍适用且没有待答问题时继续该阶段；原来在等待回答或方案已变时恢复确认门，不能因“继续”就消除待答项，也不能重复提交仍运行的作业。

### 提问工具与问题组织

先检查当前 harness 的工具和模式限制。有允许此用途的原生问答工具时使用它（例如 `AskUserQuestion`、`request_user_input_async`）；无可用工具或工具不允许确认类问题时，用清楚的文本问题。不得为调用工具强行切模式或虚构工具名。

一轮优先 1–3 个当前阶段的关键问题。长参数表先展示，确认整份方案而非逐个参数提问。已知事实直接预填并注明来源；后续阶段参数到达该阶段再展示。不要求用户重复回答事实，但不能把已知事实等同于接受当前方案。

## 配置展示与归档

训练和评测先读 [训练选项](training-options.md)、[评测选项](evaluation-options.md)，只列实际实现和所选路线支持的字段。以匹配的项目示例为起点，说明重要偏离；区分配置类默认值、示例显式值、用户指定值和 agent 建议值。凭据只引用变量名。

每个业务阶段保留自己的方案版本（包括仅研究或仅分析）。按 [任务记录](task-record.md) 存放 `configuration.md`，同一 `data` 阶段内不同业务步骤也不能互相覆盖：

| 项目 | 本次值 | 来源、影响与偏离理由 |
| --- | --- | --- |
| 目标、输入/版本、策略、关键参数 | 实际值；未知写未确定 | 用户指定／已确认方案／示例／建议 |
| 资源、预算、成本、交付终点 | 实际值；未知费用保持未知 | 约束如何落实、产物位置 |
| 当前确认 | 等待用户接受／已接受并引用决定 | 方案版本、回答和授权范围 |

全套阶段展示项和示例见 [工作流](../../../docs/zh/agent.md)。配置表字段都填完不等于用户已确认；生成方案、写配置与离线预检完成后仍需核对确认状态。

## Progress board：只在进度发生变化时显示

面板用于展示**用户请求的交付进度**。使用 `text` 代码块，每步一行，放在阶段更新的开头；标题和步骤跟随用户语言。直接调用单个阶段时用该 skill 的步骤，多阶段任务由入口维护一张总面板，阶段 skill 不再打印第二张重复面板。

标记：`[ ]` 尚未开始；`[~]` 正在处理；`[x]` 该步骤的请求终点已核查并交付；`[-]` 不在本次范围或已明确跳过；`[!]` 等待输入、中断或失败，必须附文字区分原因。

```text
DecisionForge 进度
[x] 0. 明确流程与资源
[x] 1. 数据准备
[~] 2. 完成训练
[ ] 3. 评测与比较
[-] 4. 深入分析（本次未请求）
[ ] 5. 归档与交付
```

**显示条件：** 首次明确流程；步骤标记变化；用户改变范围导致分支变化；等待/失败原因变化；用户明确询问进度。新会话接续先核查实际状态，再显示一次恢复后的面板。

**不显示条件：** 同一阶段的步数、loss、耗时更新；无变化的轮询；重复提醒；对同一个问题继续解释。可简报“训练仍在进行，step 20/100，最近 loss …，检查时间 …”，不要重复整张面板。未知进度写未知，不按经过时间编百分比；不能为触发面板而把每次轮询建成新步骤。

### 面板与任务状态的对应

| 实际情况 | 面板 | 持久状态 |
| --- | --- | --- |
| 仅启动请求已确认正常运行 | `[x] 训练启动与交接`，旁注明 `run: running；模型 pending` | `request.status=fulfilled`，stage/run 仍 `running` |
| 要求完成训练，进程活跃 | `[~] 完成训练` | 请求仍 `pending`，run `running` |
| OOM，等待选择调整方案 | `[!] 训练（OOM，等待方案选择）` | run 保留 `failed` 的事实；stage/request 可 `waiting_input`，记录证据 |
| 运行终态和产物已核查 | `[x] 完成训练` | run/stage `completed`；只有全部请求交付后 request 才 `fulfilled` |
| 未请求的阶段 | `[-] 训练（未请求）` 或从独立阶段面板省略 | 不向 `request.stages`/`stages` 添加未请求阶段 |

仅启动请求交接后不为刷新面板而擅自延长监管；后续用户要求查状态时再核查。后台 shell 的 exit 0 或 harness 的后台工具完成通知，不代表训练/评测进程结束。面板标记不是新的 task.json 状态枚举，不能把 `[x]` 或 `skipped` 写入运行状态。

README 保存最近的交付进展和实际运行状态，task.json 保存事实与决定；不用新增第二套可与 manifest 矛盾的进度状态服务。
