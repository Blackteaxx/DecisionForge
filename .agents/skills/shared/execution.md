# 执行与监管规则

执行时同时遵守 [提问、配置选择与进度面板](interaction.md)。默认每个业务阶段先展示方案并取得接受；只沿用仍覆盖当前具体方案的授权，总体路线确认不代替阶段确认。面板表示交付进度，不能替代进程、manifest 和产物核查。

## 请求范围与资源

读取用户当前请求、已有任务记录和授权。先查文件和项目事实，再问缺失决定；不重复问已经确认过的配置。研究建议、准备数据、启动运行、完成运行和分析建议是不同交付终点。

实际执行资源必须由用户指定，形式不限。可沿用此前指定的机器、SSH 主机、GPU、队列、API 服务或环境；不能因为当前机器可用就视为已授权资源。资源不明确时，可继续离线检查和准备方案，依赖资源的执行等待用户指定。训练要求 NVIDIA CUDA；Windows 原生支持 Unsloth 单卡 LoRA，其余方法使用 Linux；Unsloth full 与 Laya 支持单机 DDP，OpenJev 仅单 GPU，默认 LoRA 保留单卡执行。资源形式不限并不改变后端能力。评测按所选 adapter 检查 HTTP 或本地模型要求。

确认 harness 是否有联网、文件、终端、远程访问及必要监控能力。缺少工具时报告具体缺口和已能完成的部分。跨阶段任务按已确认路线逐阶段调用，并在新业务阶段执行前应用共享确认门。默认不要调用会连续执行生成、训练、评测的 [非交互 workflow](../../../docs/zh/quickstart.md) 绕过阶段停点。用户明确选择全程自动执行且具体配置/资源授权覆盖全部阶段时，才可按其要求使用现有串联入口；不把“完整流程”推断为这种授权。

已给预算、设备和其他限制必须沿用。生成的 USD 预算需要配置覆盖实际模型的 pricing；没有定价不能声称硬预算生效。依赖的限制无法落实时，在相关操作前说明并取得替代方案；预算耗尽时保存状态，不自行提高预算或从头重跑。

## 从仓库已有能力开始

先从现有 CLI、公开 API 和配置寻找合适的做法。任务脚本通常只需做来源格式转换、命令编排和结果整理；生成、检查、恢复、训练和评分已有实现时，沿用仓库流程即可，不必在案例里再维护一套。

如果目标确实超出现有能力，先说明哪些部分可直接完成、还缺什么，再按用户已授权的范围选择最小扩展。通用能力适合补回仓库，任务专用转换和 benchmark 接入则留在案例目录，并说明它们与原生流程的关系。

## 路径、配置与执行证据

在仓库根目录使用用户指定的 Python 环境，先核对 `uv run dforge <command> --help` 与相关项目文档。YAML 内相对路径按 YAML 所在目录解释。复制示例到任务目录时必须重写或明确解析数据、模型、映射、输出等路径，不能只复制后执行。CLI 的 `--run-dir`、`--input`、`--output-dir` 等覆盖按实际帮助和实现核对；不要发明不存在的参数。

把实际使用的配置、stdout 和 stderr 保存到阶段目录。远程配置中的路径按远程环境填写；本地副本保留远程路径，不伪装成可在本地直接运行。记录命令返回的实际目录、退出码、资源、作业标识及时间。凭据只引用环境变量名或现有凭据机制，不把值写进配置、命令记录或报告。

新训练和新评测的程序输出目录必须为空。统一将控制文件放在 `training/<run-id>/` 或 `evaluation/<run-id>/`，把实际 `output.directory`（训练）、`output`（评测）或 `--run-dir` 指向其尚未使用的 `run/` 子目录。配置为 `config.yaml`，stdout/stderr 日志放在该子目录外的同级位置；不能先在 `run/` 中写配置、重定向日志或放 PID 文件。底层程序会自行保存运行配置。恢复时使用已有实际 `run/`，不再按新运行处理。

目录出现、进程返回 PID、最后一条 loss 或启动命令退出，都不足以证明任务成功结束。调用后读取实际 manifest、报告、日志和所需文件；部分失败、暂停、预算耗尽与效果未达标分别说明。各模块状态拼写不必与任务索引相同，转换时保留原始状态及证据。

## 启动与持续监管

启动请求：检查当前进程/作业状态和正常启动日志，再交付资源、运行标识、配置、日志、查看/恢复方式及最近检查时间。保持 run 为 running；未产生的模型/报告为 pending。

完成请求：观察状态、进展和关键异常直到终态，再检查完整交付。先检查再决定等待时间，按任务时长退避，避免无意义的紧密轮询。按依赖顺序进入已请求下游阶段的方案确认；上游失败或暂停不能继续训练、评测假定成功的产物。

当前会话继续可检查时，继续监管。只有 harness 实际支持并已建立相应检查机制时，才承诺会话结束后的自动跟进；不要只开后台进程就声称会持续监管。需要但无法持续检查时，记录为尚未交付的完成请求，保存最后观测和接续方式，准确交接。恢复会话先重新检查资源，防止重复启动。不能把一个静态 SOP 当作调度器。

## 可直接处理与需要方案的变更

| 情况 | 动作 |
| --- | --- |
| 指定环境缺少既定依赖、临时连接故障、配置路径定位问题 | 在现有版本约束和授权范围内修复，记录操作与结果 |
| 原配置中断且存在兼容完整 checkpoint | 使用项目原有恢复方式，先检查身份与状态 |
| OOM，需要调整 batch size、精度、序列长度或模型 | 提出具体方案，说明对实验的影响；已有明确授权时按授权执行 |
| 标签含义不清、需要丢弃样本或重标、改变 split | 等待会改变任务含义的决定，保留原始材料与现有结果 |
| 修改指标、评测集、比较口径、扩大资源或预算、修改源码 | 展示具体差异与理由并等待接受；仅沿用明确覆盖该变更的已有授权 |

修复不等于任意升级依赖或改变实验配置。连续重复的同类失败不以无限重试处理；保留失败证据、检查点和修复方案。不能通过关闭 checker、绕过可比性检查或隐藏失败来宣布成功。

## 交付

更新 [任务记录](task-record.md) 和 README，给出用户请求终点的实际进展、产物入口、外部引用、失败/待决定事项及继续方式。报告每项验证的实际范围：离线预检不等于模型加载、GPU 运行或答案事实核验；分析假设不等于已确认原因。

需要对外分享或提交时，按 [自包含交付目录](delivery.md) 汇集源码、配置、结果与细节说明；不要提交 `outputs/`，也不要把其中的私人文件设为阅读交付的必要条件。
